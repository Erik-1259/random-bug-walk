# Bug request contract enforcement

This map lists each requirement of the bug request contract [`bug-request/1`](bug-request-v1.md) (revision 2), the layer that enforces it, the component responsible for it and the tests that cover it. It describes the contract package at this revision and the producers in the pull requests listed under [Components](#components). The producer entries change as those pull requests land.

## What each layer covers

- **Generated types** (`packages/factory-contract/src/generated.ts`, rendered from the schema). They fix field names, required fields, literals, enumerations and nullability at compile time, and they narrow an `Event` by its `type`. They do not check patterns, numeric ranges, list lengths or any rule that ties one field to another, and TypeScript refuses unknown fields only on object literals. A value that type-checks can still break the schema. [Known differences](#known-differences-between-the-generated-types-and-the-schema) lists where the types are weaker.
- **Runtime schema** (`packages/factory-contract/schema/bug-request-v1.schema.json`, checked with `@rbw/factory-contract/validate`). It refuses unknown and missing fields, wrong types, bad patterns and out-of-range numbers, and it checks the cross-field rules that JSON Schema can express within one payload, which the [package README](../../packages/factory-contract/README.md) lists. It enforces once-per-value rules over closed value sets, such as at most or exactly one entry per `host_id` or per `bug_type_id` in a list, with one `contains` clause per value. It cannot compare a payload with stored state or with another response, check that values from an open-ended set are unique by one field (`item_key` among the items, `candidate_id` among the candidates, `case_id` among the cases), add up the entries of a list or check their order by position, read configuration such as the limits, or observe time and HTTP behavior. The README lists those rules under "Rules outside the schema". A value that passes the schema is well formed. It is not thereby correct.
- **Producer.** The code that builds a value owns every rule the schema cannot express: arithmetic, identity, idempotency, ordering, locking, time limits, HTTP status codes, session access and client behavior. Only that code's own tests, and the acceptance runner against a running service, cover these rules.

A passing schema or type test is not behavioral coverage of a producer rule. The contract tests show that the schema refuses a bad value. They do not show that a producer never builds one. Each row below names the producer's tests separately, and a row that names none has none.

Test files are named without their directory: contract tests are in `packages/factory-contract/test/`, factory core tests in `packages/factory/test/`, service tests in `packages/web/test/factory-server/`, UI tests in `packages/web/test/`, worker tests in `tools/controller/test/unit/`, spend tests in `packages/spend/test/unit/`, package tests in `tools/case-package/test/` and `tools/case-validate/test/`, and the acceptance checks in `tools/product-acceptance/src/`.

## Producer responsibilities

- **Contract owner** (`packages/factory-contract/`, `docs/product/`): keeps the schema, the generated types and the fixtures in step (drift check, fixture table), states in the package README every rule the schema cannot express, and settles the open wording points below: catalog availability in sections 4.2 and 6, the hash ingredients of section 6, the unit of `max_description_chars` in section 4.3, and whether a `202` start may already be `finished` in section 7.
- **Backend lane, factory core** (`packages/factory/`): limits, unique item keys and description normalization before interpretation (sections 3 to 6); criteria matching, problem arithmetic, eligible-source counts and the interpretation hash (section 6); the request loop's order, with one candidate at a time, cell checks before assignment and storage before delivery (sections 6.3, 10 and 10.5); identity and deduplication (section 10.4); the projection's counts, paging, delivery and funnel (section 8); budget arithmetic and candidate admission (section 8.5); stop handling (section 9).
- **Backend lane, service routes** (`packages/web/src/factory-server/`): the session cookie and access rules (sections 3 and 13); body checks before the lock, the idempotent start under the ID lock and the order of its steps (section 7); error codes and HTTP status codes (section 12); downloads checked against the announced hash and size (section 10.2); the scope and order of validation IDs (section 11); refusing test mode in production, and the test controls (section 15.1).
- **Backend lane, worker** (`tools/controller/src/factory-*.ts`): heartbeats and the lost-worker finish (section 8.1); the launch, reservation, settlement and lost-run finish of validation runs (section 11); reconciliation (section 8.5).
- **Backend lane, spend** (`packages/spend/`): gapless event numbers, `request_accepted` as event 1, the events allowed after `request_finished` and one stop per request (sections 8.4 and 9); atomic acceptance (section 7).
- **UI lane** (`packages/web/src/factory/`, `packages/web/src/components/factory-*.tsx`): request and validation identity before each POST, polling and backoff, the download gate and its labels, and the example's label (sections 3, 7, 10, 11 and 14).
- **Umami lane and custom host lane** (`packages/host-umami/`, `packages/host-task-report/`): baselines, catalogs, availability, and presentation text without evaluator material (sections 4.1, 4.2 and 10.1).
- **Package lane** (`tools/case-package/`, `tools/case-validate/`): the pair binding and pair hash, the contents of each part, and the harness result from the six cells (sections 10.3 and 11).
- **Acceptance lane** (`tools/product-acceptance/`): exercises the rules above against test mode (section 15.1).
- **Publisher of the completed example** (section 15 does not name one yet): the example's two `download_path` values are URLs that need no session (section 10.2), differ from each other, since clients keep the two downloads separate (section 10.1), and are not blank. The schema refuses only an empty path and a path of exactly the site-relative live route form.

### Where a producer differs from the text

- Sections 4.2 and 6: `packages/factory` counts only the entries available in the planned window, marks a declared pair unsupported while none is available, and hashes the profile and the available entry IDs into `interpretation_sha256`. The text counts catalog entries and names only the input and the versions as hash ingredients. Owner: contract owner, with the backend lane.
- Sections 4.3 and 7: test mode checks a start's limits inside the lock after the existing-ID lookup, so an out-of-limits start that reuses an ID answers `409 idempotency_conflict` instead of `400`, and it does not check unique item keys on a start. The factory core counts description length in code points, while test mode and the UI count UTF-16 code units.
- Section 8.1: the factory core projection derives `worker_unresponsive` from the clock with no `attention` event. The service status port appends the event first, so the two together would show it twice.
- Section 8.2: the factory core projection counts a selected candidate as explored before its checks start. Test mode counts it once checks start.
- Section 8.5: when the worker settles a validation run above its worst case after the request finished, nothing sets `attention` to `needs_reconciliation`.
- Section 11: the worker prices a validation reservation from the validator package's copy count, not from the frozen interpretation's `worst_case_per_validation_microusd`. Test mode uses its profile figure, which equals the fixtures'. After reconciliation, a run whose spend was uncertain keeps `cost_microusd: null`.
- Section 15.1: the acceptance runner is pinned to an earlier contract revision, never calls capabilities or the session, sends no out-of-limits body, and its `sources-exhausted` probe sends an input that matches no fixture.

## Known differences between the generated types and the schema

The generated types are weaker than the runtime rules in these places. Code that builds a value from the types alone can produce one that the schema refuses.

- Formats: `Uuid`, `Sha256`, `ItemKey`, `Description`, `UtcTime`, `Identifier` and the download paths are `string`, so the patterns, lowercase forms, trimming and the live route template exist only in the schema.
- Numbers: `MicroUsd`, `PositiveInteger`, `NonNegativeInteger`, quantities, counts, `size_bytes`, `entries`, `next_after` and `poll_after_ms` are `number`, so integers and ranges exist only in the schema.
- List sizes: `RequestInput.hosts` has no length or uniqueness, `items`, `criteria_met` and `eligible_sources` have no minimum, `events` has no maximum, `case_ids` has no uniqueness, and the capability lists, type totals and worst-case lists are plain arrays without their once-per-value rules.
- Conditional fields: `Interpretation.startable`, `InterpretedItem.status`, `Problem.severity` and `Problem.item_key` are independent of the problems and codes; `RequestStatus.outcome`, `stop_reason`, `delivery`, `attention` and the budget's `overrun` are independent of the state, the counts and each other; `Candidate.reason`, `item_key` and `case_id` are independent of the stage; `CandidateEndedData.reason` and `RequestFinishedData.stop_code` are any value of their enumeration.
- Cases: `Case.item_key` and `Provenance.request_id` are nullable whatever the origin, `ExampleResponse.case` is any `Case`, `Case.validation` is a run or `null` whatever the request's state, `PackagePart.ready` is a `boolean`, and the slot, `kind` and `format` of a part are not tied together.
- Validation runs: `result`, `matrix`, `finished_at` and `cost_microusd` are nullable independently of `state` and `result`, and `result` is not tied to the matrix. `Cell.matches_expectation` is a `boolean`.
- Errors: `ErrorBody.details` is a union independent of `code`, and `retryable` is a `boolean` not tied to the code or to the busy reason.
- Test mode: `TestOperation.settled_microusd` is nullable whatever the state, and the two `TestSlot` holders are independent.
- Unknown fields: TypeScript refuses them only on object literals, while the schema refuses them everywhere.

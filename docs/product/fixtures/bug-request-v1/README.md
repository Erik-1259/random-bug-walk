# Fixtures for `bug-request/1`

These are representative bodies for the contract in [`../../bug-request-v1.md`](../../bug-request-v1.md). Each JSON file is one response body, except `start-request.json`, which is a request body. The endpoints are planned. The fixtures show shapes and states, not measured results. They follow revision 3 of the contract.

All values are synthetic. Request IDs follow the pattern `00000000-0000-4000-8000-0000000001nn`, validation IDs follow `00000000-0000-4000-8000-0000000002nn`, test-mode root executions follow `00000000-0000-4000-8000-0000000003nn`, and test-mode execution IDs follow `00000000-0000-4000-8000-0000000004nn`. Hashes and test-mode ledger operation IDs, which are 64 lowercase hex characters (section 15.1 of the contract), are a repeated two-character pattern (operation IDs `3a3a…`, `3b3b…` and so on), catalog and suite IDs start with `synthetic-`, and amounts are invented. Message text is illustrative, because clients branch on codes and never on messages.

How the files relate:

- `start-request.json`, `status-queued.json`, `status-running.json`, `status-fulfilled.json` and `status-validated.json` follow one request (`…000000000101`) from start to finish and then through three validation runs. They all carry the body of `interpretation-supported.json`, and the earlier event lists are prefixes of the later ones.
- `status-cancelled.json` sends the same input as a separate request, so it carries the same interpretation and hash. The other status files are separate requests with their own inputs.
- The validation files refer to the two cases in `status-fulfilled.json`. `status-validated.json` shows their reservations and costs in the request's budget and events.
- `example.json` shows the task-report case under its published-example provenance. It has the same `case_id` as the live case because both are the same case.
- Each supported combination has a one-entry catalog, so several scenarios try the same entry. Its check outcomes differ between scenarios on purpose. The exception is `status-duplicate-defect.json`, from the test-mode `duplicate-defect` scenario, whose task-report catalog has a second entry that plants the first entry's defect. Section 15.1 of the contract maps each test-mode scenario to the fixture whose `interpretation.input` it sends and the fixture that shows its end state.
- `test-evidence.json` is the test-mode evidence for the request in `status-operational-error.json`.
- Candidate IDs (`e1…` task-report entry 01, `e2…` Umami entry 01, `e3…` task-report entry 02) differ from defect IDs (`da…`, `db…`).
- Amounts follow section 8.5 of the contract: in every `budget_updated` event and status `budget`, committed = reserved + spent and remaining = budget − committed. Worst cases: the worker $0.20; a candidate $0.60 on Umami and $0.30 on task-report; a validation run $0.30 on Umami and $0.20 on task-report. Where the worker is confirmed stopped, it settles at its full worst case just before `request_finished`. In `status-operational-error.json` the worker is lost after missed heartbeats, so its reservation and the in-flight candidate's stay held until reconciliation.

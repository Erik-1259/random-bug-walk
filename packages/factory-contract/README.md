# @rbw/factory-contract

The machine-readable form of the bug request contract `bug-request/1` ([`docs/product/bug-request-v1.md`](../../docs/product/bug-request-v1.md), revision 2) and of the factory's internal data shapes: a JSON Schema, TypeScript types generated from it, type-only interfaces for host adapters and copy runners, and a validator. It defines shapes only; it has no endpoint, handler or other behavior.

## Schema source

`schema/bug-request-v1.schema.json` is the one machine-readable source. It is JSON Schema 2020-12 and follows the conventions of `@rbw/schema`: every object forbids unknown fields and requires every field, a nullable field holds `null`, and every pattern starts with `^` and ends with `$`. Under `$defs` it defines:

- the common types: `Uuid`, `Sha256`, `UtcTime` (milliseconds and `Z`, with the calendar check of the format `rbw-utc-time`), `ItemKey`, `Description` (the normalized form of a request description: trimmed and never empty), `MicroUsd` (never negative) and `SignedMicroUsd` (only for `remaining_microusd`, which an overrun makes negative), `GitCommitId`, `ImageDigest`, `RelativePath` (a relative source path with no empty, `.` or `..` segment, no backslash and no control character; route segments such as `[id]` and `(group)` and dotfiles are allowed), `AbsolutePath` (a path inside a copy: `/` followed by segments under the same rules), `Identifier` and `Version`;
- every enumeration of the contract, each listed once, such as `HostId`, `BugTypeId`, `ProblemCode`, `RequestState`, `RequestOutcome`, `StopCode`, `CandidateStage`, `CandidateReason`, `EventType`, `ValidationResult`, `ErrorCode` and `TestScenario`;
- the response and request bodies: `Capabilities`, `RequestInput`, `Interpretation`, `StartRequest`, `RequestStatus`, `ValidationRun`, `ValidationStartRequest`, `StopRequest`, `ErrorResponse`, `SessionRequest`, `SessionStatus` and `ExampleResponse`, with their item types such as `Criterion`, `Candidate`, `Case`, `Cell`, `Packages` and `PackagePart`. `RequestInput` is the input as a client sends it; `NormalizedRequestInput` is the form the service interprets, which `Interpretation.input` carries (section 6);
- the test-mode shapes of section 15.1: `TestEvidence` (with `TestOperation`, whose `operation_id` is the spend ledger's 64-hex operation ID, `TestSlot` and `TestProviderCall`), `TestReconcileRequest` (answered by a `RequestStatus`), `TestResetRequest` and `TestResetResponse`;
- `Event`, a union discriminated by `type`. Each variant fixes the shape of its `data`; `EmptyDataEvent` covers the types whose data is `{}`, and `HostEvent`, `CandidateEndedEvent` and `AttentionEvent` cover the types that share one data shape;
- the internal data shapes, which never reach a client: `BaselineIdentity`, `CatalogEntry` (with `CatalogPresentation`, the only client-safe text of an entry; an entry names the criteria it targets, and each criterion's `failure_code` is published in `Criterion`, section 6.3), `Protocol`, `FileSet`, `BugCaseInputs`, `ValidatorInputs`, `UnpackedPair`, `CopyPlan` (with `CopyDestinations`, the absolute paths inside the copy for the app files, the evaluator files and the results), `CopyRoots` (the local directories a runner reads a copy's files from), `CollectedCopy` (what a runner brings back from one copy), `CellObservation`, `CopyRecord` and `QualificationRecord`.

The contract's cross-field rules that JSON Schema can express are conditional subschemas. Each condition requires the fields it tests, so a missing field is reported once, as missing, and triggers no rule:

- `RequestStatus`: `outcome` and `stop_reason` are set exactly in state `finished`, the stop code belongs to the outcome (section 8.1), and `fulfilled` has `delivery: "complete"`. `cases` is empty exactly when `delivery` is `none` and holds only live cases, the frozen interpretation is startable, and a response holds at most 200 events. At most one candidate is in progress (stages `selected` through `packaging`), because version 1 runs one candidate at a time (section 10.5), and none once the request is finished. A frozen interpretation whose items carry `budget_below_item_minimum` or `quantity_exceeds_source` rules out `fulfilled` (section 6.2). An overrun with an outcome other than `operational_error` happened after the request finished: the outcome stays, and `attention` is `needs_reconciliation` (section 8.5). `RequestFinishedData` applies the same outcome table. `delivery` follows the counts (section 8.1): `complete` exactly when no item and no type total is missing a case, `none` exactly when none has a delivered case. A status lists at least one item; each bug type has at most one total, a type that an item requests has one with `requested` at least 1, and a type that no item requests has `requested` 0 if it is listed (section 5). The funnel agrees with the lists (section 8.2): cases mean a qualified candidate and every funnel count at least 1, no cases mean no qualified candidate and `packages_ready` 0, a candidate checking or further on means `candidates_explored` at least 1, one past its behavior checks means `behavior_checks_passed` at least 1, and an assigned candidate means `requested_criteria_passed` at least 1. Event 1 is `request_accepted` (section 7), so `next_after` is at least 1. A response holds at most one `request_finished` event, only in state `finished` and with the status's stop code, at most one `stop_requested` event, only in states `stopping` and `finished` (sections 8.4 and 9), and validation events only in state `finished`, since the request holds the slot until it finishes (sections 8.5 and 11); for the same reason, no case has a validation run before then. Candidates, cases and events name only selected hosts, and candidates, cases and `source_exhausted` events only bug types that an item requests (sections 1 and 5). A `duplicate_defect` skip comes with the earlier candidate that tried the defect (section 10.4).
- `Candidate`: `reason` is set exactly for the stages `rejected`, `invalid`, `incomplete` and `skipped`, with a reason of that stage (section 8.3); `item_key` is `null` before `requested_criteria_passed` and set from that stage through `qualified`, and `null` for a candidate rejected because a cell did not match in export verification (the original-suite and check reasons and `bug_not_detected`), since assignment needs all six cells to match (sections 6.3 and 8.2), for a candidate that fits no item (`wrong_failure`) and for one skipped before it runs (`duplicate_defect`, `no_budget_for_candidate`), since none of them was assigned (sections 8.5, 10.4 and 10.5); a candidate has a case exactly when it is `qualified`, since only a qualified candidate becomes one (sections 10 and 10.5). `CandidateEndedEvent` and `QualificationRecord` apply the same reason table to their type and verdict.
- `Capabilities`: `hosts` lists every `HostId` and `bug_types` every `BugTypeId` exactly once, since clients build the request form from this response and never hard-code hosts or types (section 4); `combinations` lists every (host, bug type) pair of `HostId` and `BugTypeId` exactly once (section 4.2); `difficulty_options` lists every `DifficultyOptionId` exactly once, so `source_inferable_allowed` is offered as the available default and `source_only_difficulty_required` is listed (section 4.4). Each list holds as many entries as its enumeration has values, with one `contains` clause per value at exactly one match. `Combination`: a supported pair has a source with at least one entry and no reason; an unsupported pair has a reason (its source may be declared or `null`).
- `DifficultyOption`: `source_inferable_allowed` is the default and available; `source_only_difficulty_required` is unavailable and not the default (section 4.4).
- `RequestBudget`: `remaining_microusd` is negative exactly when `overrun` is true.
- `RequestInput` and `StartRequest` accept any description text or `null`; the service trims it and maps an empty result to `null`. `NormalizedRequestInput`, `InterpretedItem` and `ItemProgress` hold only that normalized form (section 6).
- `Problem`: the severity follows the code (section 6.2); `budget_below_minimum` has no item, every item-level code has one, and `host_unused` may have either. `InterpretedItem`: unsupported exactly when it has a blocking problem; a supported item has at least one eligible source, and every eligible source has at least one entry (its `entries` counts the source's catalog entries that satisfy the item's criteria); an item has no eligible source exactly when it carries `unsupported_combination` or `no_matching_source`, and `no_matching_source` also needs a recognized criterion (section 6.2); eligible sources are at most one per host (sections 4.2 and 6.1); an item requires source-only difficulty exactly when it carries `unsupported_difficulty`, and is then unsupported (sections 4.4 and 6.2); an item without a description has no criteria and no unmatched text, and an item has unmatched text exactly when it carries `unrecognized_description`, which makes it unsupported; each entry starts and ends with a letter or digit, since it runs from an uncovered word to the last word of its run (section 6.1); `budget_below_item_minimum` appears only on an item with an eligible source; every problem in an item's list names an item. `Interpretation`: startable exactly when no request-level problem is blocking and every item is supported, and its request-level `problems` have no item. It interprets at least one item, and a request item that asks for source-only difficulty has an interpreted item that requests it, and the reverse, so it is never silently downgraded (section 4.4). Each bug type has at most one total, a type that an input item requests has one of at least 1, and a type that no item requests has 0 if it is listed (section 5). `unsupported_combination` on one item of a bug type is on every item of that type, and `quantity_exceeds_source` on every supported item of that type, since both are computed per bug type (section 6.2). Eligible sources are on selected hosts, and when no item lists a selected host among its eligible sources, `host_unused` appears at either level; `host_unused` appears only when some selected host is listed by no supported item, so an interpretation in which every selected host serves a supported item never carries it (section 6.2). A host that a supported item lists among its eligible sources has an entry in `budget.worst_case_per_validation_microusd`, since a validation run reserves the worst case of its case's host from that list (section 11). `InterpretationBudget`: each worst-case list holds at most one entry per host. `ItemDifficulty`: source-only difficulty is `unsupported`, the default is `not_required`.
- `ItemProgress`: `requested` is the item's quantity, so at least 1; `case_ids` lists each delivered case once and is empty exactly when `delivered` is 0 (sections 8.2 and 10.5).
- `Cell` and `QualificationCell`: `matches_expectation` is true exactly when `observed` equals `expected`. Every cell's `expected` follows the qualification table (original suite: pass, pass, pass; verification checks: pass, fail, pass), and every cell of a `Case` and of an `accepted` `QualificationRecord` matches.
- `Packages`: the bug case and validator slots hold parts of their kind, each kind has its format, and both parts are ready and have a non-empty `download_path`, since a case appears only once it is qualified and its parts are ready (section 10) and every case part has a download route or public URL (section 10.2); a live case's parts have the paths `/api/factory/requests/{request_id}/cases/{case_id}/packages/bug-case` and `.../validator`, and a published example's parts never use those routes, which need a session, since the example's URLs need none (section 10.2). `Provenance`: a live case names its request and a published example names none (sections 10 and 14); a `Case` has an item exactly when it comes from a live request, and lists at least one criterion in `criteria_met`, since a qualifying candidate demonstrates at least one (section 6.3); `ExampleResponse` carries a published example.
- `ValidationRun`: `result` and `finished_at` are set exactly in state `finished`; a run that has not finished has no matrix and no settled cost, and a `passed` or `failed` run has one (section 11). `passed` has a matrix whose six cells all match; `failed` has a matrix whose cells all observed `pass` or `fail` with at least one mismatch; `error` has no matrix or a cell that observed `error` or `incomplete` (section 11).
- `TestSlot`: a validation run that holds the slot names its request, so `holder_validation_id` is set only with `holder_request_id`.
- `TestOperation`: `settled_microusd` is set only in state `terminal`, once settled, and in state `reconciled`, which always records it, since an operation not yet settled or reconciled holds its reservation (section 15.1).
- `CollectedCopy`: `results_sha256` is set exactly when `results_dir` is, since it hashes that directory.
- `CopyRecord`: `evidence_sha256` is the collected `results_sha256`, so it is `null` for a copy that brought back no results (such as a `setup_failed` copy, which becomes an `invalid` record); a `complete` record has one.
- `ErrorBody`: `busy` carries `BusyErrorDetails` (`active` is retryable, `needs_reconciliation` is not), `interpretation_stale` and `unsupported_request` carry the interpretation (not startable for `unsupported_request`), every other code has `null` details, and `unavailable` is retryable.

### Rules outside the schema

JSON Schema cannot compare one field with another, count across a list or observe behavior over time, so the schema does not check: unique `item_key` values within a request; the budget arithmetic of section 8.5 (`committed = reserved + spent`, `remaining = budget - committed`); the exact counts behind `delivery` (`delivered` against `case_ids`, `missing` against `requested`, each type total against the sum of its items, the funnel counts against the candidates and `packages_ready` against `cases`), beyond which of them are zero; that an interpreted item matches its input item, that a case fills only one item and that the identifiers in a live download path are the case's own; event numbering without gaps and `next_after` against the last event returned, beyond event 1 being `request_accepted`; that only `budget_updated`, `attention`, `attention_cleared`, `validation_started` and `validation_finished` events follow `request_finished`, and that each response's events are a prefix of a later response's (section 8.4); that every change of `attention` has its `attention` or `attention_cleared` event (section 8.1); `candidate_id` values unique within a request (section 8), and distinct `case_id` and `defect_id` values among a request's cases (section 10.4); `runs_valid` against `runs_total`; how a qualification verdict follows from its cells, failure codes and criteria; every limit read from `Capabilities` (item count, quantities, description length after trimming, budget range); distinct failure codes among the criteria; validation-run idempotency (a `validation_id` scoped to its request and case, checked before the slot and budget, with nothing recorded for a refused run) and liveness (heartbeats at least every 30 s, `error` after 180 s without one or after 1800 s), section 11; and the test evidence's sums against the request's budget (section 15.1). Those belong to the code that produces the values.

[`docs/product/bug-request-v1-enforcement.md`](../../docs/product/bug-request-v1-enforcement.md) maps each requirement of the contract to the layer that enforces it (generated type, runtime schema or producer), the component responsible for it and the tests that cover it. It also lists where the generated types are weaker than the schema and where a producer differs from the document.

## Derived file

```
pnpm --filter @rbw/factory-contract run generate
```

writes `src/generated.ts` from the schema with `scripts/render.ts`: one type per definition, a `<NAME>_VALUES` list for every enumeration (for example `HOST_ID_VALUES`), `DEF_NAMES` and `DefTypes`. Descriptions become doc comments. The drift check in `test/drift.test.ts` renders the file again and fails when the committed file differs. The file starts with a neutral `Derived from ...` header and holds no timestamp.

## Imports

`@rbw/factory-contract` (`src/index.ts`) exports the generated types and value lists and the type-only interfaces of `src/adapter.ts`. It has no runtime dependency, so client components can import it:

```ts
import type { RequestStatus, Event } from "@rbw/factory-contract";
import { HOST_ID_VALUES } from "@rbw/factory-contract";

function label(event: Event): string {
  if (event.type === "check_finished") return `${event.data.check_set} on ${event.data.copy}: ${event.data.outcome}`;
  return event.message;
}
```

`src/adapter.ts` declares `HostAdapter` (baseline, catalog, protocol, optional availability, bug case and validator inputs, copy plans, `collect` of one copy's results into a `CopyRecord`, interpretation of copy records) and `CopyRunner`. `run(plan, roots)` places the plan's files from `roots` at `plan.destinations` after checking each sha256 (a mismatch is `setup_failed`), runs the command within `plan.limits`, copies the results directory back and resolves with a `CollectedCopy`; it rejects only for an uncertain provider outcome. The harness maps the copies of a state with `copyPlans`, runs each with `run` and parses it with `collect`, and after the last copy of the state calls `interpret`.

`@rbw/factory-contract/validate` (`src/validate.ts`) is for servers and tests. It reads the schema file next to its source when it loads and compiles it with Ajv (draft 2020-12, strict mode, with the `discriminator` keyword so an `Event` is checked against the variant its `type` names):

```ts
import { assertContract, parseContract, validateContract } from "@rbw/factory-contract/validate";

validateContract("StartRequest", body);           // [] when valid, otherwise error codes
const status = assertContract("RequestStatus", value); // narrows, or throws ContractError
const input = parseContract("RequestInput", text);     // JSON text; ContractError(["json"]) when it is not JSON
```

Error codes have the form `schema:<instance path>:<keyword>`, with the field name added for an unknown field (`schema:/:additionalProperties:extra`) or a missing one (`schema:/:required:poll_after_ms`). Because the validator reads a file at load time, a Next.js server that imports it lists the package in `serverExternalPackages`, as the web app does for `@rbw/schema`. `@rbw/factory-contract/schema.json` names the schema file itself.

## Tests

```
pnpm --filter @rbw/factory-contract test
```

- `test/fixtures.test.ts` maps every file in `docs/product/fixtures/bug-request-v1/` to its definition in one table, checks that the table lists exactly the files present, and validates each one; it does the same for the synthetic internal-shape examples in `test/fixtures/`.
- `test/invalid.test.ts` refuses variants of valid fixtures: unknown and missing fields, wrong enumeration values, bad hashes, UUIDs, item keys, descriptions and times, out-of-range numbers, and each cross-field rule above. Each variant must fail with its expected errors, and any other error must be an enclosing report (`if`, `anyOf`, `oneOf`, `contains`, `not`, or the `type` report of a nullable field's null branch) on the path above them. A rule written once per host or bug type is tested for each, on fixtures with their two hosts or bug types swapped. It also accepts variants that the contract allows, so the schema is not stricter than the document.
- `test/rules.test.ts` reads the code tables of the contract document (sections 6.2, 8.1, 8.3, 8.4, 12 and the scenario table of 15.1) and the value lists of `TestEvidence`, checks that the enumerations list the same values, and checks that the schema accepts exactly the severity, item level, stop codes and stage the tables give each code, and that a finished status's `request_finished` event names the status's stop code. For each test-mode scenario it checks that the input fixture's `interpretation.input` is a valid input and that each end-state status fixture has the outcome, stop code, delivery and attention of its row.
- `test/drift.test.ts` is the drift check, plus the schema conventions (strict JSON, anchored patterns, closed objects, each enumeration listed once, one `Event` variant per event type, `NormalizedRequestInput` identical to `RequestInput` apart from descriptions) and the client-safety check of `src/index.ts`, `src/adapter.ts` and `src/generated.ts`.
- `test/types.test.ts` checks the generated types at compile time, such as narrowing an `Event` by its `type`.

# @rbw/factory

The factory's core logic for the bug request contract `bug-request/1` ([`docs/product/bug-request-v1.md`](../../docs/product/bug-request-v1.md), revision 2): the criteria catalog, capabilities, request interpretation, the canonical start, the factory's identities, budget admission, assignment, the qualification verdict, the request loop and the request status projection. Every side effect is injected (the event store, the spend ledger, the stop check, the export-verification harness, packaging, evidence storage and the clock), so the web service and the hosted worker share one implementation. The shared shapes come from `@rbw/factory-contract`; this package defines no copy of them. It holds no limit, envelope or worst-case number: those come from the injected factory profile.

## Modules

| Module | What it does |
| --- | --- |
| `criteria-catalog/v1.json`, `src/criteria.ts` | Criteria catalog version 1: the two bug types, three criteria (each with a version, label, description, at least four example phrases and the failure code the real checks report) and the interpreter's filler phrases. `parseCriteriaCatalog` checks a catalog (known bug types once each, unique criterion IDs and failure codes); `criteriaCatalogV1()` reads the file once. Every function takes the catalog as an argument, so tests can inject the fixtures' catalog. |
| `src/capabilities.ts` | `buildCapabilities` (contract section 4) from the host registry, the catalog, the profile and an injected clock. A combination is supported when its source has an entry that the host's `availability` allows for the planned span (now to now plus `max_wall_clock_s`); otherwise it carries the host's reason. |
| `src/match.ts` | Interpreter `criteria-match` version 1 (section 6.1): exact phrase matching on words (maximal runs of letters and digits, compared case-insensitively), every word covered by a criterion phrase or a filler phrase, and each maximal run of uncovered words reported as the description's text. |
| `src/input.ts` | Request input validation against the contract schema and the profile's limits (section 4.3), normalization (descriptions trimmed, empty to `null`), and `canonicalStart`: the start body validated (unknown and missing fields refused) and the SHA-256 of its canonical body, for the idempotency check of section 7. |
| `src/interpret.ts` | `interpret` (section 6): items, criteria, unmatched text, eligible sources, every problem code of section 6.2 (`quantity_exceeds_source` counts distinct defects, and how many units they can fill), budget worst cases from the profile, and `interpretation_sha256`. |
| `src/identity.ts` | The only implementation of `defect_id`, `case_id`, `candidate_id`, the environment hash, the two UUIDv5 namespaces, the request and validation roots, a copy's execution ID and the factory project ID. |
| `src/budget.ts` | Budget admission before each candidate: the request budget's room and the pool's available amount must both cover the candidate's worst case (otherwise it is skipped with `no_budget_for_candidate`); a halted ledger, a halted pool or an overrun admits nothing. |
| `src/assignment.ts` | Assignment order (items with more criteria first, then request order), the criteria a candidate demonstrates (only those whose published failure code was observed on the buggy copy), the item a candidate fills (contract section 10.5), and candidate selection in catalog order. |
| `src/verdict.ts` | The qualification verdict (stopped, export mismatch, invalid, rejected with the first reason of section 8.3, incomplete, or matched; invalid and incomplete evidence never become a rejection) and the qualification record. |
| `src/orchestrator.ts` | `runRequest(deps)`: the request loop described below. |
| `src/projection.ts` | `projectStatus` (section 8) from the request record, its events, the stored case evidence, the latest validation run of each case, the heartbeat, the ledger's budget status and a clock (a candidate counts as started once its reservation or its own progress follows its selection; it counts in `candidates_explored`, and is in stage `checking`, from its first `check_finished`, so one that was only selected, or reserved and then stopped, skipped or halted before any check, is never explored and stays `selected` until it ends; a ready package counts once its case is delivered); `workerAttentionEvent` (raise or clear `worker_unresponsive` from the heartbeat age, each event dated by the heartbeat it reports, so repeated and concurrent polls build identical events) and `lostWorkerEvents` (the events of the lost-worker finish that the request still lacks, so a retried finish appends only the rest). |
| `src/service.ts` | `serviceFunctions`: capabilities, the interpretation of a request body and the canonical start, bound to one registry, catalog and profile. |
| `src/testing/` (`@rbw/factory/testing`) | Synthetic adapters and entries (with a `collect` that reads a fake copy's result file), a test profile with the contract's test-mode worst cases, a deterministic harness, a deterministic copy runner that follows the copy runner convention (each file's sha256 checked before placing, a fresh results directory brought back, a rejection only for an uncertain outcome), the named scenarios of contract section 15.1 for both, and an in-memory ledger and event store (the event store follows the factory event table: a replay is compared without its time, and only budget, attention and validation events follow `request_finished`). |

## The request loop

`runRequest` takes the frozen request, the host registry (adapters in catalog order), the catalog, the profile and the ports in `src/ports.ts`. It appends `host_preparing` and `host_ready` for each host it will use, then for each candidate:

1. Stops when a stop is recorded (`cancelled_by_user`, checked first, so a stop recorded before the finish wins over a filled request), every item is filled (`fulfilled`) or the deadline passed (`time_limit`). A stop or the deadline found while a next candidate would still run (an item is short, an entry is left and the candidate limit is not reached) finishes `operational_error` instead when the run's latest ledger read showed a halt, a halted pool or an overrun, since that would stop the same candidate (the order of a copy boundary); the loop does not read the ledger again for this.
2. Selects the next entry: for the items with an unfilled unit in assignment order, the first untried entry in catalog order that declares every criterion of the item. None left: `source_exhausted` for each source that was fully tried, then `sources_exhausted`, or `budget_exhausted` when a short item's entry was skipped for budget. The candidate limit counts started candidates. Only then, with work still to do, a halted ledger, a halted pool or an overrun stops the request `operational_error`.
3. Appends `candidate_selected`. An entry whose defect an earlier candidate of this request already started with is skipped (`duplicate_defect`). A worst case the budget or the pool cannot cover is skipped (`no_budget_for_candidate`), as is a reservation the ledger refuses for budget or pool; a refusal because the ledger is halted ends the candidate incomplete (`stopped`) and stops the request `operational_error`.
4. Reserves the candidate's worst case (the sum of its protocol's copies at the host's copy envelope), reads the ledger and appends the reservation's `budget_updated`; a halt, a halted pool or an overrun that read finds ends the candidate incomplete (`stopped`) before export verification runs, and it settles and the request finishes `operational_error`. Otherwise it runs export verification through the injected harness. Before every copy it checks, in this order, whether an earlier copy's ledger read found a halt, a halted pool or an overrun (which stops the candidate as a stop does and finishes the request `operational_error`, also when a recorded stop or the deadline is found at the same boundary), the stop record, and that the copy's timeout fits before the deadline; after every copy it reads the ledger and appends `budget_updated` when the amounts changed, and after the last copy of a state it appends that state's two `check_finished` events from the cells the harness reports for the state (`onCells`, with the protocol's floor applied), which are the cells the verdict reads.
5. Applies the verdict. The harness's return is a matched candidate's last check boundary, with the same checks in the same order: a halt or an overrun the last copy's ledger read found, or a stop recorded while that copy ran, ends it incomplete (`stopped`), never delivered (contract sections 8.5 and 9), and the request finishes `operational_error` or `cancelled_by_user`. The deadline bounds only what starts (a copy, a candidate): a matched candidate whose copies all started in time is delivered, and the loop's checks then stop the request `time_limit` unless every item is filled. A complete verdict that is not a match keeps its reason, and the loop's checks decide the request's code. Otherwise it gets `behavior_checks_passed`; it is assigned to an item (`requested_criteria_passed`) or rejected with `wrong_failure`. An assigned candidate is packaged, its evidence (the client-safe case and the qualification record) is stored, and `package_ready` and `case_delivered` follow. The stored parts must be the pair export verification ran on: the bug case is the archive it ran on, the stored validator holds the validator core it ran on plus this qualification record as its evidence member, as packaging reads them back from the stored bytes, and the reported `pair_sha256` is the canonical digest of the case ID and the two stored parts' SHA-256 values (contract section 10.3). Otherwise the candidate is rejected with `export_mismatch` (the exported parts failed their integrity check, contract section 8.3) and nothing is delivered.
6. Settles the candidate and appends `budget_updated`. An overrun that any ledger read of the request showed, after a copy or at this settlement, finishes the request `operational_error` now (contract section 8.5), ahead of a filled request, a recorded stop or the deadline, so the budget closes with that code; the finish checks again once the worker settled. An overrun once seen stays seen: a ledger that releases a candidate's unused copy reservations when it settles can end the overrun, and the request still finishes `operational_error`.

A rejection of the harness, of a reservation or of a candidate's settlement is an uncertain outcome: the loop appends `attention` (`needs_reconciliation`), never retries and finishes `needs_reconciliation`, leaving the reservation held. A failed check between copies (the stop record or the ledger could not be read) stops the harness, and a failed stop check once the copies ran stops the candidate; either way the candidate ends incomplete, settles, and the request finishes `operational_error`. Any other failure inside the loop (a port read, an adapter) ends the candidate in flight as incomplete and finishes `needs_reconciliation` while its reservation is held, otherwise `operational_error`; a held reservation whose `budget_updated` is missing is recorded before that end, from a fresh ledger read or, when the ledger cannot be read, from the amounts the run last recorded; a failure while finishing propagates, and the lost-worker finish then applies. The finish settles the worker through the ledger port, reads the ledger and appends `request_finished`: a failed worker settlement is uncertain and finishes `needs_reconciliation` with the worker's reservation held; otherwise an overrun any read of the run showed, from the reservation, a copy, a candidate's settlement or the worker's own, finishes `operational_error` even when the last read no longer shows it, and so does a failed read or budget event after the worker settled; otherwise the loop's stop code stands. The worker's settlement closes the budget with the code known before it settles, an overrun seen by then included. Between the loop's last ledger read and that settlement only the worker itself runs (preparing hosts, checking, packaging), and its use settles there, so the budget closes with the code `request_finished` names unless the worker's own settlement overruns or the read or budget event after it fails. The result says whether the slot must stay held and lists caught failures for the operator's log. Check output, observation detail and failure codes never enter an event message, a candidate or a case.

A halted ledger or a halted pool stops only work still to do: a copy, the qualification of a matched candidate whose reservation's or copy's read found it, or a next candidate. A halt found together with a recorded stop or the deadline at the top of the loop, while a next candidate would still run, stops that candidate as they do and comes first (step 1). A halt that a read shows only after the last needed case settled, or when no next candidate would run (no entry left to try or the candidate limit reached), stops no work: the request keeps its outcome and the budget closes with that code, as contract revision 2 keeps the outcome for an overrun found after the request finished. An overrun, by contrast, finishes `operational_error` whenever a read before `request_finished` shows it.

Where several stops end the same work, at a candidate's check boundary or at the top of the loop, the request's code follows one precedence: an uncertain outcome (`needs_reconciliation`), then an overrun, then a halt or a failed check (`operational_error`; a failed read while a candidate's reservation is held and unsettled finishes `needs_reconciliation`, as above), then a recorded stop (`cancelled_by_user`), then the deadline (`time_limit`). A candidate stopped before its last check boundary ends incomplete and is never delivered; a stop found once a candidate passed it (`behavior_checks_passed` appended) does not end that candidate, which step 5 decides, and decides only the request's code. `test/stop-rule.test.ts` runs every stop source (a recorded stop, the deadline, a halted ledger, a halted pool, an overrun, an uncertain outcome, a failed stop read, a failed ledger read) at every point of a request (before the first candidate, after the reservation, between copies, during the last copy, during packaging, after `package_ready` and at the top of the loop), and pairs of them, as one table.

The loop appends every request event except `request_accepted`, `stop_requested`, the start reservation's `budget_updated`, `worker_started`, the validation events and the lost-worker finish. Event keys are deterministic and unique per request; `src/events.ts` lists the scheme.

## Ports

| Port | Behavior the loop relies on |
| --- | --- |
| `EventSink.append(event)` | Assigns `seq`; the same `event_key` with the same content replays, different content conflicts. |
| `RequestLedger` | `status()` reports the budget's reserved and spent amounts, the halt state and the pool's available amount; `reserveCandidate` is the hard bound behind the pre-check; `settleCandidate` and `settleWorker` settle. An implementation that reserves per copy inside the runner may answer `reserved` and reserve per copy: the loop reads `status()` after every copy. |
| `QualifyHarness` | Runs export verification for one entry with the `beforeCopy`, `onCopy` and `onCells` hooks and resolves with the harness result, its identity and whether the archives passed their integrity checks; it rejects only for an uncertain provider outcome. |
| `PackageCase`, `writeEvidence` | Store the case's two parts (the validator archive is the core plus the qualification record) and the per-request evidence. `PackageCase` reports the hashes of the stored bytes, and for the validator also `core_sha256` (the core the stored archive holds: the archive without its evidence member, packed as a core is packed) and `evidence_sha256` (its evidence member), each null when that part is missing. |
| `FactoryProfileInput` | `profile_sha256`, `limits`, `worker_worst_case_microusd`, and per host `copy_envelope_microusd` and `validation_worst_case_microusd`. |

## Held

Wiring the real export-verification harness to `QualifyHarness` is held. This package's tests and test mode use the deterministic harness in `src/testing/`. The `validatePair` result, as its interface is specified today, has no harness identity and no integrity outcome, and the port needs both: `harness` for the qualification record, and `integrity` so that a refused or mismatched pair ends `export_mismatch` (rejected) instead of `setup_failed` (invalid). The wiring is one adapter function. It looks up the entry's two archives, passes the three hooks through, and fills `harness` and `integrity` from fields the harness reports. It stays held until the specified interface has those fields and the harness is on the same base as this package. Until then, a pair refusal that a harness reports only as `result: "error"` with a null matrix gets the verdict `invalid` (`setup_failed`), never `rejected`.

## Tests

```
pnpm --filter @rbw/factory test
```

The tests reproduce every interpretation fixture and `capabilities.json` from synthetic adapters and the test profile, reproduce every `status-*.json` fixture from its event sequence, run every named scenario of contract section 15.1 through the loop with the deterministic harness and check the end state's outcome, stop code, delivery, attention, stages and counts against its fixture, and validate each produced shape with `@rbw/factory-contract/validate`. Counting, assignment, verdicts, stop paths and budget admission have their own tests. All data is synthetic; nothing calls a network service.
